# 현재 구현 전체 검수 결과

검수일: 2026-09-25 ~ 2026-09-26 (한국 시간)

대상: `feature/accessibility`, 제품 코드 기준 `2e28aaf`의 메인 앱 및 저장소의 별도 STT/LLM/UI 프로젝트.
환경: Android 16/API 36 x86_64 에뮬레이터 `AEMX_TTS_API_36`, 교보문고 3.2.23 (`mok.android`). 최초 검수 시 알라딘은 설치되어 있지 않았다. 2026-09-27 후속 검증은 [ALADIN_VALIDATION.md](ALADIN_VALIDATION.md)를 참조한다.

## 판정

메인 앱의 실행 계층·TTS·로그인 정보 저장 기능은 아래 범위의 자동 검사를 통과했다. 2026-09-26에는 실제 교보문고 로그인 화면을 확인하고 아이디 칸 식별을 수정했다. 교보문고가 에뮬레이터에서 보안 차단 팝업을 표시해 실제 인증 성공은 확인하지 못했다. 전체 음성 명령 → 실제 서점 로그인/검색/구매까지 완료된 제품으로 판정하지 않는다.

## 발견한 문제와 후속 작업

### 1. LLM의 의미적 target과 실제 UI 식별자 사이의 변환이 없다

`LLM/system_prompt.txt`는 `검색창`, `검색`, `검색결과 첫번째 항목`을 출력하지만 `NodeFinder.kt:22-38`은 text/contentDescription/hint/resource ID의 정확한 일치만 허용한다. 이번 교보문고 화면에서 관측한 검색창 ID는 `searchMainKeyword`, 검색 버튼 라벨은 `search button`이었다. 따라서 스키마가 맞는 JSON이라는 이유만으로 실제 화면까지 실행된다고 볼 수 없다. 앱·화면별로 검증한 target 매핑과 중복 요소 처리 기준이 필요하다. 부분 문자열로 무조건 클릭하도록 완화하면 오조작 위험이 생긴다.

### 2. 시작 광고 팝업이 있으면 검색 입력이 timeout 된다 — 에뮬레이터 재현

교보문고 홈의 광고 팝업이 열린 상태에서 `open_app → input_text(searchMainKeyword) → tap(search button)`을 실행했다. 앱은 열렸지만 입력 단계가 8초 후 실패했다. 팝업을 수동으로 닫고 재실행하면 검색어 `데미안` 표시와 세 단계의 UI 명령 전달 완료 로그를 확인했다.

검색 결과 목록 도착을 이번 실행의 통과 조건으로 확정하지 못했다. 앞서 사용자가 검색 동작을 확인한 사실은 유지하되, 이번의 명령 수락 결과와 합쳐 E2E 통과로 집계하지 않는다. 팝업 처리·화면 준비 조건·검색 결과 확인을 별도 단계로 보강해야 한다.

### 3. UI 명령 수락과 업무 성공 판정이 분리되어 있다

`ACTION_CLICK`/`ACTION_SET_TEXT`의 true 반환 후 계획이 끝나며, 로그인 성공/실패 메시지·로그인 사용자 표시·검색 결과·구매 결과를 확인하지 않는다. 현재 UI의 '실제 결과 확인 필요' 문구가 정확한 제한이다. 계정 잠금, CAPTCHA, OTP는 검증하지 않았으며 자동화하지 않았다.

### 4. STT 녹음의 Activity 종료 처리가 없다 — 정적 코드 검수

`STT/SherpaOnnx/app/src/main/java/com/k2fsa/sherpa/onnx/MainActivity.kt:136-162`에서 녹음 중지·AudioRecord 해제는 버튼을 다시 누를 때만 수행한다. 클래스에 onStop/onDestroy 해제가 없고 recordingThread 종료를 기다리지 않는다. 녹음 중 화면 종료/회전 또는 빠른 중지·재시작 시 녹음 자원과 스레드 수명이 Activity와 어긋날 수 있다. 모델 파일이 없어 해당 현상을 이번 기기에서 재현하지는 않았다. 통합 전에 생명주기 정리와 재시작 테스트가 필요하다.

### 5. LLM 손상 모델 복구 경로가 부족하다 — 정적 코드 검수

`LLM/LlamaDemo/app/src/main/java/com/example/llama/MainActivity.kt:110-112`는 파일 크기가 0보다 크면 기존 모델을 재사용한다. 로딩 실패 후 해당 캐시를 폐기·재다운로드하는 경로가 없고, 149행의 rename 결과도 확인하지 않는다. 손상된 파일이 남으면 재실행해도 같은 파일을 다시 읽게 된다. 무결성/다운로드 완료 검증과 실패 시 복구 동작을 확인해야 한다. 실제 모델 추론 검사는 이번 범위에서 실행하지 못했다.

### 6. 실제 로그인 검수는 교보문고 보안 차단으로 완료하지 못했다

사용자가 AEMX에서 실제 교보문고 계정을 등록했고 암호화된 파일 존재만 확인했다. 교보문고 3.2.23의 로그인 화면에서 라벨 없는 아이디 칸 하나, 비밀번호 칸 하나, `loginBtn`을 확인했다. 첫 실행은 아이디 칸 식별 실패로 계정 제출 전 중단됐다. 이를 수정하고 기존 서명으로 AEMX를 업데이트했지만, 후속 실행은 교보문고의 `보안`·`차단`·`종료` 팝업으로 중단됐다. 실제 인증 성공은 확인하지 못했다. 알라딘은 이번 검증에서 제외했다. 실제 로그인 정보는 Git·검수 로그·JSON에 기록하지 않는다.

## 이번 검수에서 변경한 것

- 제품 기능 코드는 변경하지 않았다.
- 실행기 검사에 스크롤 방향·숨김 컨테이너 제외, 거절된 UI 명령 timeout, credential 예외의 비밀 비노출 검사를 추가했다.
- TTS 실제 한국어 재생과 빈 입력 계측 검사를 추가했다.
- 외부 검사 앱은 기존 Activity가 열린 상태에서도 메인 화면부터 시작하도록 CLEAR_TOP을 적용하고, 오래된 상태 문구 대신 중단 요청 응답으로 실제 서비스 연결을 확인하도록 바꿨다.
- 외부 검사 오류를 finish 이전에도 기록하도록 개선했다. 이전 검수의 외부 검사 미완료 상태는 이번 5개 통과로 갱신한다.
- `kyobo_search`는 검색 재현을 위한 수동 결과 확인 도구다. 출력의 DISPATCHED는 검색 성공 판정이 아니다.

## 재현 명령

```sh
./gradlew :app:assembleDebug :app:testDebugUnitTest :app:lintDebug :app:assembleDebugAndroidTest :accessibility-device-tests:assembleDebug :accessibility-device-tests:lintDebug
adb shell am instrument -w -r com.sihoo.aemx.test/androidx.test.runner.AndroidJUnitRunner
adb shell am instrument -w -r com.sihoo.aemx.devicechecks/.DeviceChecks
adb shell am instrument -w -r -e scenario kyobo_search com.sihoo.aemx.devicechecks/.DeviceChecks
```

APK는 동일한 서명을 유지해 업데이트 설치한다. 같은 프로세스 계측 검사 후 접근성 서비스 연결이 끊기면 에뮬레이터 재시작으로 기존 사용자 활성화 상태를 복원한다. 검수 중 서비스를 설정에서 강제로 켜거나 계정·앱 데이터를 지우지 않았다. 실제 화면 덤프는 민감 정보가 있을 수 있어 Git에 포함하지 않는다.
